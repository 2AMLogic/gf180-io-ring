## What has no evidence, and why

- **Post-layout (item 7).** Every row's post-layout cell reads `no evidence`: the manifest cites no post-layout extraction, so there is nothing to aggregate. That column is tracked in issue #21 and is deliberately out of scope here. A `no evidence` cell is never a pass.
- **Declared gaps.** 2 of the 22 spec rows carry a `gap` string in the manifest and are reported as `no evidence`, quoting that string as their parameter. The gap set is read from `spec_rows["5"][*].gap` on every build, never hard-coded, so this report follows the manifest when a gap is closed or added:
  - `esd_core_rail_clamp`: core VDD-VSS rail clamp (3.3 V devices) not simulated: the spec gives no voltage budget for it
  - `esd_vdd_dvdd_coupling`: VDD/DVDD cross-domain coupling is not drawn yet (spec: decision record to follow)

## Methodology

### Where each number comes from

- **The row spine** is the manifest's `spec_rows["5"]`, in manifest order. `spec/io-ring.md` names its parameters in prose and carries no row ids, so the spec section is linked for the human-readable parameter and the ids come from the manifest.
- **Limits** are read from each cited envelope's `measurements[].limits`. This report holds no copy of a ratified number; a limit that changes in the spec reaches this table only by way of a re-run bench and a re-cited envelope.
- **The binding corner** is the cited measurement instance closest to its own limit, normalized by that limit. The normalization matters: one envelope carries nine supply instances whose trip-point limits scale with `DVDD`, so the smallest absolute margin is not always the binding one. This is the same reduction [`sim/gpio-corners/collect.py`](../gpio-corners/collect.py) applies, and its `ROWS` measurement table is imported from there rather than retyped.
- **Content hashes are not verified here.** The manifest's item-5 `content_hash` is the envelope's own `environment.netlist_sha256`, not the sha256 of the cited file, and item-6 citations carry none. Artifact freshness is `klt signoff`'s job, enforced on every PR by [`.github/workflows/signoff.yml`](../../.github/workflows/signoff.yml).
- **The row-to-file mapping is asserted, not derived.** The manifest states which spec rows each envelope is evidence for (`klt signoff` records every item-5 row source as `asserted`), and this report inherits that assertion. It checks the mapping for consistency -- a cited row no measurement can supply, or a measurement whose base name is unknown, fails the build -- but it does not independently prove that a given envelope measures the row it is cited for.

### The alias map

Item 5 names measurements and item 6 splits the pull devices into their own spec rows, so both have to be joined onto the spine. That join is this map, and it is the one design decision in this report:

| Measurement-derived or item-6 row id | Spine row |
|---|---|
| `esd_pad_dn` | `esd_pad_clamp` |
| `esd_pad_up` | `esd_pad_clamp` |
| `esd_rail` | `esd_rail_clamp` |
| `pulldown_3v3` | `pull_3v3` |
| `pulldown_5v` | `pull_5v` |
| `pullup_3v3` | `pull_3v3` |
| `pullup_5v` | `pull_5v` |

A row key that this map sends to a row the manifest does not cite it for is a hard error, not a silent drop; so is a measurement base name absent from `ROWS`.

### Monte Carlo is not corner coverage

Every cited yield campaign samples the **`typical` process section only** (`measurements[].source_corners`), so an item-6 figure can never stand in for an item-5 corner verdict, and a row with a Monte Carlo cell but no corner cell is not covered across process. The temperatures actually cited differ per row and are printed in each cell: the output-level and transfer rows are cited at three temperatures, the pull-device rows at 25 C alone. Where a row's cited campaigns disagree, the cell reports the weakest of them (lowest confidence-interval low bound).

### The two columns do not always share a limit

4 rows carry a different limit in the two columns, and the Monte Carlo cell renders its own limit inline for them:

| Row | Corner-matrix limit | Monte Carlo limit |
|---|---|---|
| `vil_5v` | >= 1.35 V | >= 1.5 V |
| `vih_5v` | <= 3.15 V | <= 3.5 V |
| `vil_3v3` | >= 0.891 V | >= 0.99 V |
| `vih_3v3` | <= 2.079 V | <= 2.31 V |

Both are correct readings of the one ratified rule (VIL <= 0.3 * `DVDD`, VIH >= 0.7 * `DVDD`): the corner matrix evaluates it at the binding `DVDD` extreme, the Monte Carlo campaign at nominal `DVDD`. Neither is relaxed and neither is reconciled here -- reconciling them would be a spec change, which belongs in a decision record.

## Regenerating this report

    sim/characterization/run.sh           # rewrite report.md and report.json
    sim/characterization/run.sh --check   # fail if the committed report is stale

`--check` runs on every pull request. Any change to [`manifests/gf180-io-ring.json`](../../manifests/gf180-io-ring.json) -- a new citation, a closed or added `gap`, a re-pointed record -- must be accompanied by a regenerated report in the same pull request, the same obligation the committed `klt signoff` record already carries.
